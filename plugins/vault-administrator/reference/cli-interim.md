# Vault CLI: what to do when a command misbehaves

Read this before a pull or a push. Each row is a behavior of the current CLI and what to do
instead. The last column is the check that shows a newer CLI build has fixed it; when that
check passes on the build in use, the row no longer applies and the plain command is right.

| What you see | What to do instead | Retire when |
|---|---|---|
| A push that includes a Custom Page bundle fails on the distribution upload with `METHOD_NOT_SUPPORTED` | Push the components, then upload the bundle with `vault api -X POST -F "file=@<distribution>.zip" "/uicode/distributions/"`: a multipart POST with the zip as the `file` part, which adds the distribution or replaces one of the same name and answers `ADDED`, `MODIFIED`, or `NO_CHANGE`. Under Git Bash set `MSYS_NO_PATHCONV=1`. Build the zip with `Compress-Archive` run from PowerShell, or with Python, since `zip` is not installed | A push of a workspace with one new page distribution deploys the page and prints no error |
| A push reports an error on a class under `javasdk/` while the components in the same push deploy | Upload the class on the documented single-source-file call, `vault api -X PUT -F "file=@<path>/<Class>.java" /code`, one call per class, then push the rest; or move the code in a package, imported and deployed with Import Package and Deploy Package | A push with one changed class under `javasdk/` deploys it and prints no error |
| A push or pull that lists errors or skipped components still ends with "Push complete." or "Pull complete." | Read the errors and skipped blocks above the last line; never take the last line or a 0 exit code as the result | A push or pull that lists an error no longer ends with "complete" |
| A pull writes a multi-value list attribute with doubled quotes, `('A'', ''B')` | Leave the file as the pull wrote it. When you reuse the value in a `vault mdl` statement, write it in standard form `('A', 'B')`. If a push fails on a component whose change is such a list, send that one change as a `vault mdl` statement | A pull writes the list as `('A', 'B')` |
| New components that depend on each other fail in one push: AI components (a tool type, a tool, an agent), and a `Page` with the Tab or Subtab that opens it ("value [Page.<name>] does not resolve to a valid [component]") | One push per dependency level, in order, with a commit and a pull between them. An object, its lifecycle, and the workflow its user action runs are not this case: they deploy together in one push | A workspace of three new components that depend on each other deploys in a single push |
| `vault config package create` lists 0 components after a push | Build the package before the push, or take the package from the source Vault's outbound export | `package create` after a push lists the pushed components, or takes a component selector |
| If a SHOW statement through `vault query` fails with an "Unknown token [PAGESIZE]" error | Use `vault api` against the metadata endpoint for the same answer | `vault query "SHOW FIELDS FROM vault_component__v"` returns rows |
| `vault query` output has no record total | `vault api -X POST -H "Content-Type: application/x-www-form-urlencoded" -d "q=SELECT id FROM <object> PAGESIZE 0" /query` and read `responseDetails.total`. Under Git Bash set `MSYS_NO_PATHCONV=1` | `vault query "SELECT id FROM vault_component__v"` prints a record total |
